# ADR-002: Publicación Asíncrona mediante Transactional Outbox

## Estado
Aceptado

## Contexto
La publicación directa síncrona de eventos a un broker de mensajería (Kafka, RabbitMQ, etc.) durante una transacción de base de datos introduce el anti-patrón de doble escritura (*dual-write*). Si la base de datos comitea pero la red falla, o si el broker responde pero la base de datos hace rollback, el sistema entra en inconsistencia irrecuperable.

## Decisión
1. **Transactional Outbox Pattern (`TRX-03`):** Todo evento de dominio emitido por un agregado se almacena localmente en la tabla `outbox_events` dentro de la misma transacción ACID de base de datos.
2. **Despacho Desacoplado con `SKIP LOCKED` (`SED-05`):** Un worker en segundo plano (`OutboxRelayService`) sondea registros en estado `PENDING` utilizando `FOR UPDATE SKIP LOCKED` para prevenir bloqueos entre réplicas horizontales concurrentes.
3. **Resiliencia y DLQ:** Los fallos transitorios se reintentan con backoff exponencial. Tras 5 intentos fallidos, el evento se mueve a `DEAD_LETTER` registrando `last_error`.
4. **Purga Automática (`TRX-06`):** Proceso cron programado que elimina registros con estado `DELIVERED` cuya antigüedad supere la retención configurada (7 días por defecto).

## Consecuencias
- **Positivas:** Consistencia transaccional estricta sin necesidad de transacciones distribuidas (2PC/XA); garantía de entrega al menos una vez (*at-least-once*).
- **Negativas:** Introduce latencia asíncrona mínima en la publicación de eventos; requiere compuertas de idempotencia en consumidores.
